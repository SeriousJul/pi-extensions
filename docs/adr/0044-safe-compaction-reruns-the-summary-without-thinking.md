# Safe compaction reruns the summary without thinking and degrades to a checkpoint

pi's compaction summarizes with the session's thinking level, but budgets the summary's output as a share of the compaction reserve: 0.8x for the history summary, 0.5x for a split turn's prefix, capped by the model's output ceiling. With the reserve at 32768 those budgets are 26214 and 16384 tokens. The budget counts thinking tokens the same way it counts summary text. A reasoning model at an effort level can spend the whole budget thinking and stop mid-summary, pi maps the length stop to "generation hit the token cap and the summary is incomplete", and the compaction fails with its retry and every retry after it, until the context can no longer fit the window at all. The reporter's sessions show exactly this: 2-message summarization requests carrying the session's xhigh level, stopping at the cap on their local 27B, no compaction entry ever recorded.

**The Safe compaction extension takes over the summary on the before-compact event when the model reasons and the session's thinking level is on: it re-runs pi's own compaction with thinking disabled, so the same prompts, budgets, and split-turn handling write summary text only. When even the thinking-free run cannot write a summary, it degrades to a deterministic checkpoint - the previous summary verbatim, the original request, a capped index of the turn's text and tool activity, and the file lists - so the compaction always completes and the session never strands in an ever-growing context.**

**Considered options.** Lowering `compaction.reserveTokens` - rejected because the budgets shrink with it: 0.8x of a smaller reserve is a smaller output budget for a summary that still has to cover the same content. Setting the session's thinking level off - rejected because it changes the model the user asked for on every turn. Raising the model's `maxTokens` - rejected because the budget is the minimum of the reserve share and the model ceiling, and the ceiling already exceeds the share; the thinking tokens are the overflow, not the ceiling. A guard that lets the built-in run and patches the failure after the fact - rejected because a failed compaction leaves the context as it was; the session keeps growing on every retry, so the fix must replace the unsafe call, not clean up after it. An upstream pi fix (budget thinking separately, or disable thinking for summarization in core) is the clean long-term home for this behavior; until it lands, the extension stands alone.

**Consequences.** Every compaction on a reasoning model with thinking on writes its summary through the extension, so the summarization's thinking level is always off regardless of the session setting; the summary quality of a thinking model is lost for that one call. The takeover runs before pi's own summarizer, so pi's failure path is never entered while the extension is on: a dead engine or an engine that fails even the thinking-free run lands on the checkpoint, which is extractive and lossy in detail. The checkpoint carries the previous summary verbatim, so nothing already summarized is lost, and the next successful compaction summarizes it away. A session with no model (initialization edge) degrades to the checkpoint as well. The handler never throws: an unhandled error would hand the unsafe native path back. The built-in summarizer runs unmodified only while the extension is disabled or while the session's thinking level is off or the model does not reason.

The re-run forwards pi's retry policy: the `retry` section of the same settings files pi reads, with the same project-over-global merge and the same defaults, so a transient stream drop in the thinking-free call spends the user's retry budget before the checkpoint. Two limits stay: the re-run cannot reach the session's stream function, it streams through pi's built-in handler for the model's API, so a session with a custom stream function (SDK, or a provider registered with `streamSimple`) runs its re-run through the built-in handler instead of its own function; and that function's provider-level transport settings (`retry.provider`) apply inside the function, so they do not apply to a re-run that uses the built-in handler.
